# deploy-notes

Сервис [notes](https://notes.kaidstor.ru) живёт в `~/Projects/own/notes` и катится на
my-vpn скриптом `./deploy.sh`: образ собирается локально, на сервер уезжает только он.
Исходников на сервере нет, откат — переключением на предыдущий тег образа.

История изменений — руками написанный массив в `src/web/lib/changelog.ts`. Ниоткуда
не подтягивается, в бандл попадает на сборке. Поэтому **запись дописывается до деплоя**:
после деплоя правка уедет только со следующим релизом.

## Шаги

1. **Собери, что уходит на прод.** Сравни с датой верхней записи changelog:

   ```bash
   cd ~/Projects/own/notes
   git status --short
   git log --date=short --pretty='%ad %s' -15
   ```

2. **Допиши `src/web/lib/changelog.ts`** — если среди изменений есть хоть одно, заметное
   пользователю глазами (вёрстка страницы, поведение индекса, новая возможность).
   Правила — в разделе ниже. Чисто внутренние правки (рефактор, деплой-скрипт, README)
   записи не требуют; скажи об этом вслух, а не молча пропусти шаг.

3. **Проверь сборку и, если менялась вёрстка, посмотри глазами:**

   ```bash
   bun run build                 # tsc --noEmit + vite build + бандл сервера
   bun run start                 # http://localhost:3000 — страницы заметок из исходников
   bun run dev                   # vite 5173 + сервер 3000 — если менялся индекс/редактор
   ```

   Правки в `src/server/page.ts` (CSS и скрипты страницы инлайнятся) видны только после
   перезапуска `bun run start` — `bun run start` без watch, старый процесс отдаёт старую
   страницу.

4. **Деплой:**

   ```bash
   ./deploy.sh --skip-dns        # DNS давно на месте, шаг с Timeweb только тратит время
   ./deploy.sh                   # полный, если поднимаешь домен заново
   ./deploy.sh --logs            # плюс docker logs после деплоя
   ```

   Идёт ~80 секунд, в конце сам дёргает `https://notes.kaidstor.ru/healthz`. Скрипту
   нужны `ssh my-vpn`, docker, `sec` (секреты) и `jq` — он проверяет это сам и падает
   с внятным текстом.

5. **Убедись, что на проде именно новый код** (healthcheck отвечает и на старом образе):

   ```bash
   curl -s https://notes.kaidstor.ru/healthz
   grep -o 'assets/[^"]*\.js' dist/web/index.html | head -1     # имя бандла из свежей сборки
   curl -s -o /dev/null -w '%{http_code}\n' https://notes.kaidstor.ru/assets/<имя>.js
   ```

   Весь сервис за токеном, поэтому 401 без него — норма, а не поломка: так отвечают и
   `/`, и страница заметки, и `/raw`. Открыты только `/healthz`, `/robots.txt` и статика.
   Проверять доступ — заголовком, через `sec run notes`:

   ```bash
   sec run notes -- sh -c 'curl -s -o /dev/null -w "%{http_code}\n" \
     -H "authorization: Bearer $NOTES_READ_TOKEN" https://notes.kaidstor.ru/<uuid>'
   ```

6. **Коммит** — по-русски, conventional commits, без `Co-Authored-By`. Одна фича = один
   коммит, changelog едет тем же коммитом, что и сама фича.

## Запись в changelog

```ts
{
  date: '2026-08-03',                       // сегодня, `date +%F`
  title: 'Блоки кода и «что нового»',       // коротко, о чём релиз
  items: [
    'У блока кода по наведению появляется панель: «копировать» и «перенос».',
  ],
}
```

- Новая запись — **первой** в массиве: порядок в файле = порядок на экране.
- `date` это идентификатор и критерий «видел / не видел» (`localStorage`,
  `notes.changelogSeen`, сравнение строк). Дата новой записи должна быть **строго больше**
  верхней существующей, иначе запись не покажется никому.
- Уже есть запись с сегодняшней датой — дополняй её `items`, а не заводи вторую.
- Формулировки — человеческим языком, от лица пользователя («по наведению появляется
  панель»), а не сообщениями коммитов («feat(page): панель у блоков кода»). Внутренности
  (`pre-wrap`, имена файлов) в текст не тащить.

## Что ещё держать в актуальном состоянии

- `skills/publish-note/SKILL.md` — при изменениях вёрстки страниц, набора классов
  (`.note`, `.cards`), API или флагов скрипта публикации. Скилл описывает, что автору
  заметки доступно в markdown; устаревший — молча уводит в старую вёрстку.
- `README.md` — при новых ручках API, переменных окружения и шагах запуска.
- `~/.claude/skills/publish-note` — симлинк на `skills/publish-note` этого репозитория:
  скилл публикации нужен из любого проекта, поэтому он глобальный, но копии нет и
  разъехаться нечему. Если симлинк заменили копией, правки в репозитории до агента не
  доедут — проверь `ls -l ~/.claude/skills/`.
- Сам этот скилл — проектный (`.claude/skills/deploy-notes`) и подхватывается только в
  сессиях внутри репозитория. В `~/.claude/skills` его быть не должно.

## Грабли

- **Деплой собирает образ из рабочего дерева, а не из HEAD.** Незакоммиченное уедет на
  прод, а закоммиченное позже — нет. Перед `./deploy.sh` смотри `git status --short`.
- **Новая обязательная переменная окружения — сначала в sec, только потом деплой.**
  `.env` на сервере собирается из sec-проекта `notes` (`sec export`), а сервер при
  `NODE_ENV=production` бросает на старте, если обязательной переменной нет. Забыл
  `sec gen`/`sec set` — контейнер уйдёт в рестарт-цикл, а `healthz` будет отвечать
  со старого образа ровно до его остановки, так что деплой выглядит успешным.
- **`bun run build` обязателен только для проверки**: Dockerfile собирает всё сам. Но
  падение `tsc` в докере обнаружится минутой позже, чем локально.
- Прод отдаёт `19 notes` и прочие цифры из своей базы — локальная `data/notes.db` к
  нему отношения не имеет. Тестовые заметки, созданные локально, на прод не попадают;
  созданные через прод-API — попадают, их надо удалять (`--delete <uuid>`).
